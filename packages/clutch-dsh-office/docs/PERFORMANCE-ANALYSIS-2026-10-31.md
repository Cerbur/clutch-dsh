# Office 性能开销分析 · 2026-10-31

分析基线：`cc59bb3`，`wt-office-0.1.0/release`。

结论：空闲重绘策略有效，但有角色时仍是偏重的3D页面。当前主要优化方向是实时阴影、
像素着色与纹理资源，其次是角色资源复用；JavaScript和绘制批次数不是这次样本的主要瓶颈。
本次仅分析，未修改正式渲染代码、模型或材质。

## 测量方法与边界

- 本机内置浏览器，Chrome156，WebGL2 / ANGLE Metal / Apple M1 Pro。
- 视口1088×950；正式上限DPR1.5，对应画布1563×1230；DPR1对照为1042×820。
- 复用实际`OfficeDashboard`、加载校验/并发控制、厨房构建、PBR、动画和阴影路径。
  单独构建临时测量页，素材通过本机HTTP按生产描述符加载；不是原生DSH整页性能测量。
- 每次预热2秒、采样8秒；CPU计时包含动画、角色位置、标签布局和同步绘制提交，
  GPU使用`EXT_disjoint_timer_query_webgl2`异步计时，非`1000 / CPU耗时`推算FPS。
- 主画面和阴影计数分开统计；静态阴影缓存刷新只出现在加载/失效阶段。
- 关闭先前的三个测试预览后采集主要样本；此前一人样本、预热结束时仍有两个角色在加载的
  DPR1无阴影探索样本均保留原始记录，但不用于主要结论或下表。
  系统其他负载未完全隔离，每个人数并非多轮随机顺序基准，不能把小差异归因于人数。
- 无加载失败或白模回退；最终浏览器warn/error为空。测试页及本机服务测完已关闭。

四人另一窗口：19.25FPS，CPU1.4ms、GPU48.56ms；复测GPU P95为51.55ms。
当前样本没有稳定达到代码设定的30FPS上限。CPU计时不包含浏览器全部布局、合成、驱动
和系统工作，因此不能将其换算为整个应用的CPU占用率。

静态厨房实际几何399,911三角形；渲染器多出的50来自透明灶台额外绘制。
每角色57,002面、3个网格、1套31骨骼及4个形态键；主画面与动态阴影各绘制一次，
因此每人每帧增加114,004个被提交三角形和6次绘制。四人的角色几何为228,008面。

空厨房不持续绘制不代表加载零成本。最后一次空场景加载失效帧记录到主画面50次、
三张静态阴影共147次绘制，总计约160万三角形；之后8秒无重绘。
模型到达会使静态阴影缓存失效，冷加载可能重复生成缓存；未对其总耗时或长任务单独归因。

## 对照：像素密度与实时阴影

| 四人对照             |  画布像素 | GPU中位数 ms | GPU P95 ms | 实际绘制FPS |
| -------------------- | --------: | -----------: | ---------: | ----------: |
| 正式阴影，DPR1.5     | 1,922,490 |        46.82 |      51.55 |       19.87 |
| 正式阴影，DPR1       |   854,440 |        32.99 |      39.66 |       25.24 |
| 关闭实时阴影，DPR1.5 | 1,922,490 |        19.95 |      24.61 |       25.87 |

DPR1.5的像素数是DPR1的2.25倍。降低像素密度能减轻GPU负担；关闭实时阴影也显著缩短
GPU时间，支持优先检查阴影系统的判断。该对照同时移除阴影生成与材质阴影采样，
不能将全部差额归因于12次角色阴影绘制，亦不能把两个时间差相加。

当前有7个RectAreaLight、1个PointLight；前三面光各配16tap软阴影采样，烘焙接收者
另有角色阴影采样。缓存静态阴影图避免重复生成，仍会在每次主画面绘制中采样它们。
关闭阴影仅为临时诊断，会改变画面，不作为本轮交付改动。

厨房GLB的40.37MB、约83.9%是内嵌图片；所有GLB合计图片42.86MB，占77.5%。
地板仅880面但文件3.69MB，其中图片3.65MB。单纯继续减面不会同比缩小下载量。

进入Office从本机Host按需取素材，不是每次从外网CDN下载58MB；安装npm包本身仍需下载。
四人样本中角色GLB只请求一次，字节缓存由四人共享；每位角色仍独立parse、图片解码和上传。
因此增加人数主要增加内存/创建开销，不会把角色下载量乘四。
本机HTTP不能代表远程部署的冷加载速度，本轮未给出可移植的首屏加载时延结论。

## 内存与资源复用

| 项目                          | 空厨房 |   四人 |
| ----------------------------- | -----: | -----: |
| 材质纹理RGBA/mipmap估算 MiB   | 397.33 | 482.67 |
| 活跃几何属性 MiB              |  10.86 |  28.39 |
| 活跃形态键属性 MiB            |      0 |  23.87 |
| 材质纹理预计独立上传数        |     74 |     90 |
| Three纹理资源计数，含内部资源 |     81 |    113 |

纹理按实际尺寸、类型、mipmap与Three上传缓存规则去重估算；包含16MiB墙地光照图，
不含内部骨骼/形态键纹理、环境/LTC、阴影、MSAA/帧缓冲、驱动布局、解码峰值等，
不是操作系统实测显存，也不能与JS堆简单相加得出总内存。
JS堆受GC和历史加载影响：空场景复测86.67MiB、四人复测233.18MiB，仅作观测值。

同款植物和椅子在房间内已共享解析资源；角色只共享原始字节，四人独立创建geometry、
morph和4张图片。若后续复用同一角色模板的只读几何/贴图，同时保持骨骼、mixer和眨眼独立，
理论可省去三份材质纹理约64MiB，以及三份几何/形态键属性约31MiB；尚未实现或实测。
实现时必须调整资源所有权，不能让任一角色退出时dispose仍被其他角色使用的资源。

程序白模替换后仍由Models持有至房间销毁，活跃几何44个而Three资源计数可达194个；
属于当前生命周期内的保留开销，不能据此直接判断泄漏。
离屏销毁GPU资源不会清除模块级原始字节缓存；全部资产的CPU字节缓存约55.64MiB。

## 后续优先级

| 优先级 | 建议                                | 主要收益与约束                                                                  |
| ------ | ----------------------------------- | ------------------------------------------------------------------------------- |
| 1      | 提供低开销阴影/像素密度档位         | 对照支持GPU收益；需审阅软阴影与清晰度变化，不能直接照搬全关阴影                 |
| 2      | 共用角色只读几何与贴图              | 减少重复解码、内存和入场创建成本；保留独立骨骼/表情及正确引用生命周期           |
| 3      | 按屏幕占用压缩纹理或采用GPU压缩格式 | 包体与显存的主要优化空间；小道具可先验证，需贴图质量与解码兼容检查              |
| 4      | 定点减面                            | 五盆植物58,915面、桌子40,396面、层架31,524面、置物柜28,794面，合计约40%静态几何 |
| 5      | 再评估合批或单GLB                   | 当前稳态主画面仅50–62次绘制、CPU较低，优先级低于上述项目                        |

鲸鱼娘提亮仅增加角色原shader中的少量漫反射运算，没有新增光源、贴图、几何或绘制批次；
本轮没有对该hook单独开关计时，不宣称其GPU耗时为零。

当前版本更适合把定位描述为“有空闲节流的完整视觉场景”，不能仅凭已降面认定为轻量。
上述优化均为分析建议，本轮保留用户确认的现有画面。
