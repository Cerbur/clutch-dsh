```bash
pnpm --filter @cerbur/clutch-dsh-title test:compat \
  --dsh-source /absolute/path/to/deepseek-harness \
  --output /tmp/title-dsh-021-delivery-matrix
```

The source checkout supplies the RC tag inventory. The runner switches the
published DSH CLI and every direct DSH development dependency to each exact RC in
a disposable workspace. It verifies installed package versions and CLI identity,
builds title from source, runs the whole package suite and typecheck, then boots
the ordinary Web profile through the real CLI and Loader. The existing DSH
checkout, title development pins, lockfile, and `~/.dsh-test` remain unchanged.

Non-DSH direct dependencies follow the repository lockfile through temporary
pnpm overrides. Without that control, the first fresh install selected a newer
Zod incompatible with DSH's fixed Zod types, which would confound the RC
comparison. No override or dependency change is added to the real workspace.

Each version owns its workspace, profile, dynamic loopback port, deterministic
LLM adapter, data, reports and logs. Runtime processes stop in `finally`; parent
interruptions terminate owned process groups with bounded escalation. Reports
publish through a temporary file and rename so polling cannot read partial JSON. The
runner fetches the browser bundle URL from DSH's own resource graph, including
its revision. It never constructs a presumed browser resource URL.

## Failure found and fixed

Both RCs initially passed all 186 package tests but rejected native Session
persistence after a repaired title:

```text
session/title-llm-request messages do not represent messageSeqs
```

The released V4 relationship validator in
`packages/session/session-format-v3-to-v4/src/relationships.ts` requires one user
message with source `dsh-session-title-llm` and one text block. Title's old repair
path logged three messages: the original user input, the rejected assistant
response, and a corrective user turn. The ordinary generation path already met
the invariant, so a successful non-repair live smoke test did not reveal it.

Repairs now retain the same single framed user message and original source seqs.
The bounded rejected response is JSON-quoted in the subsequent system instruction
alongside its rejection reason and field requirements. The recorded system and
messages remain identical to the actual dispatched request. Every repair uses
the same overall deadline and existing repair budget; token usage and diagnostics
remain per attempt. Transport errors are still never repaired.

The new prepared-call regression failed with `3 !== 1` before the fix and passes
afterwards. The real Web fixture persists the complete log through the native
JSONL backend, reopens it through the released validator, then repeats the read
after a full server restart. This extends the original compatibility plan and
supersedes its earlier assumption that a three-message repair sequence was safe.

Existing logs already written by an older incompatible repair path are not
migrated by this change. The regression verifies newly generated repaired logs.

## Coverage

In addition to the complete package suite and typecheck, each RC runs these
real-composition checks:

1. Loader activation and settings presentation on the correct owner.
2. Automatic structured title generation with exact request recording.
3. Repair, token usage and diagnostics.
4. Deterministic templates without model dispatch.
5. Disabled templates through the shared plain-title executor.
6. Manual rename pinning and explicit-refresh unpinning.
7. Transport failure without repair or replacement of the accepted title.
8. Native Session persistence and validation of repaired request records.
9. Authenticated Web HTML and its generated plugin resource.
10. Actual HTTP settings/statistics/diagnostics RPC and both reset operations.
11. Full server restart restoring the durable title and persisted resets.

The adapter is deterministic and sends no request to an external model provider.
The package's browser-bundle tests exercise client registration and generated
Remote mounting; the live HTTP checks verify delivery and Host invocation.
This matrix does not claim a separate end-to-end browser interaction test.
