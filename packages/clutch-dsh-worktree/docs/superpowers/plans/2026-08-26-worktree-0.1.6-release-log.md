# Worktree 0.1.6 Release Log and Publish Gate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prepare the 0.1.6 release metadata in an isolated feature worktree, record the release from commit history, and stop at a verified manual npm publish gate before merging the release worktree back to `main`.

**Architecture:** Start from the existing `wt-worktree-0.1.6/release` candidate and keep the changes in `wt-worktree-0.1.6/feat-release-log`. The package-level `RELEASE-LOG.md` is a bilingual repository document and is not an npm artifact; `docs/RELEASING.md` and `AGENTS.md` define the ordering and clean-worktree gates. No source inspection is needed to summarize this release: the release log is derived from commit subjects without copying commit metadata into the published text.

**Tech Stack:** Markdown, npm package metadata, pnpm workspace checks, TypeScript build, Node test runner, npm tarball preview.

## Global Constraints

- `packages/clutch-dsh-worktree/package.json` is the only version source.
- The 0.1.6 release summary is based on `git log` commit subjects between `main` and `wt-worktree-0.1.6/release`; the log contains only concise bilingual Added/Improved/Fixed/Removed sentences, with Chinese first and no commit hashes or subjects.
- `RELEASE-LOG.md` and related release documentation must be updated before the npm version is incremented and before the feature scoped release commit is created.
- The feature worktree is never a publish location; npm pack and the user's manual npm publish run only from the release worktree after the feature commit is merged there.
- Feature-to-release integration requires clean source and target worktrees, a feature rebase onto the release branch, and one scoped feature commit.
- Do not commit generated `lib/`, coverage, sidecar data, or local credentials.
