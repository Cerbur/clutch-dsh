# Worktree 0.1.4 Optimization Design

## Goal

Prepare `@cerbur/clutch-dsh-worktree` 0.1.4 as a behavior-preserving optimization release.
The release updates the workspace-wide collaboration and plugin documentation contracts,
provides English and Chinese README files with the same public facts, and reduces internal
source-module size and coupling without changing the public Remote, Client, or data-boundary
contracts.

## Confirmed constraints

- The repository root `AGENTS.md` owns branch and worktree rules for the whole workspace.
- The README framework in the repository root applies to every runnable plugin under `packages/`.
- `README.md` is English and `README.zh.md` is Chinese; both documents must be updated together.
- Existing screenshots under `assets/screenshots/` should be reused when they describe the current
  UI. The current package already has `screenshots-en.png` and `screenshots-zh.png`.
- Installation documentation lists npm installation first and repository/source installation
  second.
- The code change must preserve public exports, Remote and Client contracts, existing UI behavior,
  DSH data ownership, sidecar boundaries, and failure-recovery semantics.
- No new product capability or transport is part of 0.1.4.
- The three delivery lines are developed in three independent worktrees and merged into
  `release/0.1.4` after each worktree is rebased on the current release branch.

## Delivery lines

### 1. Bilingual plugin documentation

The README will use the following shared structure:

1. Short feature introduction with English/Chinese screenshots.
2. Capabilities and compatibility requirements.
3. Installation, with npm first and local checkout/Git source installation after it.
4. Detailed usage, with the relevant screenshots and the current UI workflow.
5. Limits, data ownership, release/development references, and marketplace copy where useful.

`README.md` and `README.zh.md` will contain the same sections, examples, constraints, and
installation sources. Translation may be natural in each language, but it must not omit or add
behavioral claims. Version numbers remain in `package.json` and release documentation rather than
being copied into README prose.

The documentation worktree changes:

- `packages/clutch-dsh-worktree/README.md`
- `packages/clutch-dsh-worktree/README.zh.md`
- only the screenshot references or assets needed to make the documented UI verifiable

### 2. Workspace collaboration rules

The root `AGENTS.md` will define the repository-wide release workflow:

- A package release branch starts from `main` and is named
  `release/<release-name>-<version>`, for example `release/worktree-0.1.4`.
- A package feature worktree starts from the release branch and uses
  `wt-<release-name>-<version>/<feature-name>`, for example
  `wt-worktree-0.1.4/feat-readme`.
- A root/workspace change that is not scoped to a package uses `base/feat-<feature-name>`.
- Each worktree is independently tested and ends as one squashed commit whose message clearly
  states its scope.
- Before merging a worktree, rebase it onto the latest release branch. The release branch is the
  aggregation boundary for the target version.
- Before npm packaging or publishing, rebase the release branch onto `main`, run the complete
  checks, and only then publish. The completed release branch is merged back into `main`.

The root README policy will require each runnable plugin package to provide the bilingual README
pair, the four required sections, screenshot references where the UI is visual, and synchronized
updates whenever public behavior changes. Package-level `AGENTS.md` files will point back to this
workspace rule and describe only package-specific facts.

### 3. Source optimization

The source refactor uses conservative seams and compatibility barrels rather than rewriting the
architecture.

#### Client surface

`src/client/WorktreeSurface.tsx` remains the stable composition entrypoint. Its implementation is
split by responsibility into focused internal modules:

- `worktree-surface-types.ts`: shared prop, state, and drag-contract types.
- `worktree-surface-selectors.ts`: pure workspace/session filtering, labels, and derived view
  calculations.
- `worktree-surface-rows.tsx`: Workspace, Main/Worktree group, Session, and session-group rows.
- `worktree-surface-dialogs.tsx`: rename, delete, create-worktree, and remove-worktree dialogs.
- `WorktreeSurface.tsx`: connection to DSH snapshots, refresh generations, mutations, and final
  layout composition.

The existing `session-view.ts`, navigation, overlay, and context modules remain browser-only and
continue to consume contract-shaped data. No Client module may import Host, Manage, Provider, or
Node APIs.

#### Client data and actions

The 370-line `worktree-view.ts` module is split into read projection, mutation/error, and move
helpers. `worktree-view.ts` remains a compatibility barrel that re-exports the current public
client-facing helper names, so existing tests and internal imports do not acquire a new API seam.

#### Manage orchestration

`WorktreeManagerImpl` remains the public implementation and `createWorktreeManager` remains the
factory. The class delegates to focused internal operation modules for:

- path, filesystem-boundary, generated-id, and provider-error helpers;
- Worktree listing, branch projection, creation, removal, and ordering;
- Session binding, workspace/session validation, and runtime cwd resolution.

The delegated functions receive an explicit internal dependency context containing DSH read ports,
Git, sidecar, DSH Home, and the ID factory. They must not expose Provider classes through the
contract or Host Remote.

#### Provider sidecar

`WorkspaceShardedSidecarRepository` and `validateSidecarSnapshot` retain their current exported
names and behavior. Sidecar schema validation, equality/mutation helpers, keyed serialization, and
atomic disk persistence may move into focused internal modules. The sidecar must continue to:

- write only plugin-owned relation data;
- validate exact schema and relation invariants;
- serialize mutations per Workspace;
- preserve DSH fixture bytes and degrade to read-only behavior when unavailable.

#### Dead-code and logic audit

The optimization worktree will remove only code proven unused by imports, tests, generated exports,
or the build/lint graph. It will consolidate duplicated selectors, error normalization, and JSX
branches only when the resulting function has the same input/output and side effects. It will not
remove a public export merely because the current package tests do not import it.

## Testing strategy

- Preserve the existing contract, provider, manage, host, client-boundary, and surface tests.
- Add focused tests for any new pure selector, manager operation helper, sidecar validator, or
  error-normalization seam.
- Update source-level tests to read the new module group when an implementation is intentionally
  moved out of `WorktreeSurface.tsx`; tests must assert behavior and module boundaries rather than
  forcing all implementation into the old file.
- Verify main, active Worktree, detached binding, idempotent binding, conflict rejection, failure
  compensation, refresh preservation, and Client disposal behavior remain covered.
- Run package lint, typecheck, build, and test, then workspace checks and `git diff --check`.

## Merge protocol

The three worktrees use these branches:

- `wt-worktree-0.1.4/feat-readme`
- `wt-worktree-0.1.4/feat-branch-policy`
- `wt-worktree-0.1.4/feat-src-optimization`

Each worktree is created from `release/0.1.4`, receives one squashed commit, is rebased onto the
latest `release/0.1.4`, and is merged into that release branch. No worktree publishes or pushes.
After all three merges, the release branch is rebased onto `main`, the full validation suite is
run, and the package is ready for the separately documented npm release procedure.
